Ниже — **структурированный и приземлённый план**, ориентированный на защиту ВКР/курсовой и на то, чтобы он соответствовал **реальной текущей реализации в проекте**.

На MVP-проходе эмоции из видео считаются в `ai-gateway` с использованием **DeepFace** и возвращаются в UI по WebSocket-событию `emotion`.

---

# 1. Подбор конкретных библиотек (что реально используется в MVP)

## 1.1 Видео: эмоции по лицу (MVP)

### ✅ DeepFace

**Назначение:** анализ изображения лица и получение:
* `dominant_emotion` (доминирующая эмоция)
* распределения/оценок по классам (`emotion`-словарь), из которого можно формировать `confidence/probs`

**Роль в проекте:** `ai-gateway/plugins/frame.py` принимает кадр от UI и отправляет событие `emotion`. Далее UI обновляет плитки и агрегирует данные в отчёт.

Почему подходит для диплома:
* готовое решение без обучения;
* понятный результат (dominant emotion + вероятность);
* легко объяснить на защите как “видео → модель → эмоции → отчёт”.

---

## 1.2 Аудио: эмоции речи (пока опционально)

Для аудио на следующих итерациях можно выбрать один из вариантов:
* `Whisper` (ASR) + анализ эмоций по тексту
* `openSMILE` / `SpeechBrain` (прямые эмоции по голосу)

В текущем MVP аудио не отправляется из UI и не используется в `ai-gateway`, поэтому это оставлено как дальнейшее расширение.

---
# 2. Архитектурная схема пайплайна (логическая)

## 2.1 Общая схема
```text
UI -> backend WS -> ai-gateway (DeepFace) -> backend WS -> UI

В UI отправляется кадр:  type="frame", payload.frame="data:image/jpeg;base64,..."
В ответ приходит эмоция: type="emotion", payload.emotion="...", payload.confidence/probs

UI обновляет плитки и агрегирует статистику в Report.
```

---

## 2.2 Что важно подчеркнуть на защите
* анализ выражений лица выполняется по кадрам на основе **предобученной** модели DeepFace;
* обработка вынесена в отдельный сервис (`ai-gateway`), что соответствует модульности архитектуры;
* отчёт формируется из реальных событий `emotion` (а не из заглушек), приходящих по WebSocket.

---

# 3. Минимальный вариант под защиту (РЕКОМЕНДУЕМЫЙ)

Это **самый важный пункт**.

## 3.1 Что делать НЕ НУЖНО

* не нужно обучать CNN с нуля;
* не нужен полноценный мультимодальный Transformer;
* не нужен real-time стриминг;
* не нужны сложные attention-механизмы.

---

## 3.2 Минимально достаточная конфигурация

### Видео (MVP)
* DeepFace (по кадрам)
* Извлекать:
  * `dominant_emotion`
  * вероятности/уверенность (`confidence/probs`)
* Агрегация:
  * частота эмоций во времени (пример: доля/количество событий в `Report`)

### Аудио и фьюжн
* Пока не реализовано в MVP.
* Следующая итерация: добавить `audio -> emotion` и затем простую агрегацию (majority/weighted average) для перехода к HR-метрикам.

---

## 3.3 Почему это легко защитить

| Критерий           | Почему хорошо      |
| ------------------ | ------------------ |
| Интерпретируемость | AU и pitch понятны |
| Воспроизводимость  | open-source        |
| Ограниченность     | нет переобучения   |
| Академичность      | классическая схема |
| Реализм            | применимо в HR     |

---

## 4. Как это связать с физической моделью

* `video_stream` (кадры от UI) → `ai-gateway` (DeepFace) → `emotion_record`
* `emotion_analysis_config` → фиксирует пайплайн
* `emotion_record` формирует данные для визуализации в `Report`
* `report.dashboard_json` → визуализация

---

## 5. Рекомендованный стек (коротко)

* Python 3.11
* DeepFace
* `ai-gateway` (WebSocket + плагинная архитектура)
* PostgreSQL (данные сессий/репортов)
* React UI (агрегация событий `emotion` и отображение)

---

## 6. Формулировка для защиты

> Для обеспечения воспроизводимости и снижения вычислительных затрат в работе используется сервисная схема анализа выражений лица на основе предобученной модели DeepFace. Анализ выполняется по кадрам, полученным от UI через WebSocket, а результаты распознавания эмоций поступают в клиент для отображения плиток и агрегации статистики в отчёте. Такой подход позволяет продемонстрировать применимость эмоционального анализа без необходимости обучения сложных нейросетей.
